### Regression cases and existing mod implications

[1.20.0.4](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1845383656396296) fixes a secondary-recipient selection bug after artifact interactions that could block education. Add the sequence “open artifact interaction → open education/other secondary-target interaction” to later acceptance tests. The release is a record of a fix, not proof that every remaining targeting problem is native or fixed.

1.20.1 also reports Study Rite balance changes and faith/rite, puppet sender, council notification and UI corrections. Recompute expected study success/costs from the **current full helper/caller chain** before using the older conversion worksheets' numbers. Existing [conversion audit](../update-readiness/mods/mass-demand-conversion-audit.md) and tests remain historically useful; this documentation operation does not re-audit or update that mod's full implementation and does not close its runtime gates.

1.20.1.2 mentions multilingual cardinal/revoke UI corrections, rite-name truncation, portrait crashes, holy-site/DLC visibility, religious-inspiration gating and adventurer inheritance. They motivate separate regression tests at relevant language/DLC/state combinations. The patch's broad save/mod compatibility wording is not a compatibility certification for the workspace mods.

## Code of Khans: contracts, overlords and state ownership

[Diary #168](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1795917897484448), 2025-04-08, explains changes later released in Chamfron. The [1.16 release](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1797820624589961) and current references refine its prerelease context. Some exact syntax/formulas appear only in screenshots; those are not reconstructed from prose here.

The complete current `common/subject_contracts/groups/_subject_contract_groups.info` distinguishes reusable contract membership, GUI layout, tributary validity/break-free conditions, map relationship lines and inheritance flags. In the documented tributary validity/break-free callbacks, **root is subject and `scope:suzerain` is suzerain**. Contract groups and individual contracts are separate databases. A tooltip or inherited government identity does not substitute for the actual relationship object.

The diary differentiates liege, suzerain, employer and overlord; it also describes obedience as a code-selected target with scripted value/threshold and migration as code-controlled initiation with script-controlled outcomes/scoring. Those historical explanations identify where to audit, not a guarantee that an ordinary interaction can reproduce migration. Read the actual migration interaction, CB, government rule and callback-supplied scopes together before changing selection or land transfer.

Domiciles are described as owned by special landless titles, superseding older character-owned assumptions. Inheritance therefore needs the title, holder and active-domicile relationship, not merely a saved character scope. Herd stored on a domicile and county fertility are different state surfaces. Exact formula constants/equilibrium and government spelling shown only in historical images are not adopted as new documentation contracts. Use current complete domicile/government/script-value/define files and lifecycle tests.

## Situations are not automatically Struggles

The current path is **`common/situation/situations`** (singular `situation`), including `_situations.info`; related catalyst/group schemas are separate. #168 describes a dynamic-region building block with subregions, phases and participant groups. It explicitly says existing Struggles were **not converted**, because their special behavior and UI differ. This corrects an easy misreading of “evolution of the Struggle system.” Keep the [archived Struggle guide](../reference/wiki-extensions.md) separate.

Current `.info` distinguishes the code-side `window` enum from `gui_window_name` and `gui_participation_window_name`. A GUI filename/widget does not expose an arbitrary controller: the code window determines available functions. Its documented triggered icon evaluates a **situation** scope. Full native situation definitions, phase/helper calls and GUI consumers are in the audit; designing a new phase cycle still needs its own entry/candidate/transition/end contract.

The source describes phases ending by duration, points, script or no successor; group membership is evaluated per subregion. Dynamic region geometry does not imply arbitrary midgame creation of every database group. The forthcoming opposite-group and title-confederation facilities in [Silk & Silver](silk-and-silver-preview.md) are later announcements, not established Crozier fields.

Current `common/confederation_types/_confederation_types.info` still documents **`house_based_confederation`**. Preserve that version distinction when studying the historical creation/member/daily-validity discussion. Do not migrate a current definition to `confederation_base` simply because #9 announces it. Actual destruction timing, member minimum and ownership after succession remain runtime checks.

## Scribe maintenance, stories, lists and performance

[Realm Maintenance I](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1826992588603740), [II](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1827626365765598) and the [final 1.19 release](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1830163047265930) separate initial ideas, beta and shipped behavior. [Spring Cleaning](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1824644522847508) is an introduction, not the final schema.

The story tracker adds presentation to existing persistent story cycles; it does not create automatic state ownership or exactly-once rewards. The complete `common/story_cycles/_story_cycles.info`, native story definitions/helpers and GUI matches document visibility, icon/background, typed visualization variables, counters, decisions/modifiers/traits, and setup/end/owner-death hooks. Types, saved variable names and localization context must match. The existing [story-state supplement](../reference/wiki-extensions.md) already covers ownership/cleanup; the new point is distinguishing visible-story UI from the underlying lifecycle. No robust cross-generation fixture is promoted to tested status.

The 1.19 release calls out ruler quick filters, dynasty iteration excluding inactive dynasties by default with `include_inactive = yes`, regnal-name APIs, saved government-type arguments, DLC-dependent building modifier overrides, skill multiplication, scope-based trait parameters and UI helpers. These overlap current Crozier reference coverage. A broad `every_*` scan copied from an older Wiki can have a different candidate set after a patch. Choose the exact documented list/filter before comparing a candidate count; do not infer iterator behavior solely from its name.

[Performance diary #187](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1813674388903190) explains candidate reduction before costly scoring, cached income and staggered rather than universally calendar-first monthly processing. [1.18.1](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1816215235351596) specifically reports cached income-trigger changes. These qualify older performance advice: an old expensive-trigger warning may no longer describe the current implementation. Measure the actual version, population, evaluation frequency and trigger order; a caching announcement is not a benchmark for a mod's repeated loops.

#187 mentions an available script profiler, while [By God Alone performance #6](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1842846814455418) explicitly illustrates internal-only mesh-streaming tools and internal profiling. Do not present every screenshot as a public console command. The general improvement discussion supports measuring and reducing work, not invented profiler syntax or guaranteed speed gains. Any profiling tools must be verified before use; none were installed or run.

No foreign asset was downloaded, copied or rendered here.

## Remaining acceptance gates

For new examples, obtain current engine/UI dumps where old exports cannot supply a signature. Establish exact callback scopes, parameter expansion, optional targets, ownership and cleanup before implementation. Then test startup, visible/hidden/disabled states, exact charges/results, repeat/invalid/dead targets, save/load and two-player routing. For art/audio, validate the actual consumer and render/playback separately. This research neither performs those tests nor clears the existing conversion, delayed-state, Knight or graphics blockers.

# Additional Wiki guidance and historical caveats

This is an authored research guide to the complete **57-page** [pinned Wiki archive](https://github.com/jesec/ck3-modding-wiki/tree/db66965014483aa1a0e0905e5a922be9ee3b9a2f/wiki_pages), retrieved 2026-10-03. The [page ledger](../research/jesec-wiki-coverage.md) accounts for every page, its provenance and destination. The archive's README synchronization claim and “timeless” labels do not certify current behavior. Existing handbooks remain the primary language reference; current engine exports and installed native audits take precedence.

## Script, weights and AI

`Commands`, `Effects_list`, `Triggers_list`, `Scopes_list`, `Modifier_list` and `Data_types` provide historical terminology and command discovery. Their large tables are **not copied as a current API reference**: use [engine lookup](index-guide.md) for category, raw source span, signature, scopes and unknown fields. `Commands` is explicitly labelled 1.0; an old claim that a command “doesn't work” is not a current failure verdict. A script effect is also distinct from a debug-console command.

The archive's `AI_modding` page separates tuning defines, eligibility and selection weights, personality values, and custom scheduled script. It describes conqueror story/effect files as a concrete workflow to study, not an API giving full control of military AI. Do not adopt its categorical “army behavior entirely hardcoded” claim as a Crozier capability audit. For a feature, read the current `.info`, the personality/value consumer and the actual decision/interaction/event selection code. Do not infer that the same `ai_chance` block grammar works in each reader. [Legacy perk AI](../systems/dynasty-legacies.md) uses Script Values; [control flow](../handbook/control-flow.md) distinguishes `base`/`factor` weighting from numeric formulas. AI weights are not independent percentage chances. Large character scans need measured performance in their actual frequency/context.

`Weight_modifier` adds useful macro orientation: ordered conditional `add` and `factor`, optional tooltip description, reusable `common/scripted_modifiers` and literal `$PARAMETER$` replacement. These are weight macros, distinct from timed character modifiers and `common/script_values`. The general rules are already covered in the handbook; inspect the caller's reader rather than moving the same macro into an arbitrary field. Existing scope/list/variable chapters retain their documented ownership and lifetime gates.

## Story cycles and state ownership

The archive's story page suggests recurring work and storage surviving a character's death. This is a **design possibility**, not automatic immortality of state or exactly-once execution. The complete installed `common/story_cycles/_story_cycles.info` documents `on_setup`, `on_end`, `on_owner_death`, `effect_group` and story-root contexts. `scope:story` is also the active story in those documented hooks. For owner changes, inspect `story_owner` and the current `make_story_owner` declaration plus actual callers.

The current schema documents fixed/ranged intervals, optional group chance and trigger, at most one independent `triggered_effect`, `random_valid` selecting at most one valid branch, `first_valid` choosing the first valid branch, and `fallback` when none fired. It also documents visible-story icons/backgrounds and typed visualization variables. The engine `end_story` entry says it executes `on_end` and makes the story inaccessible. These are declaration/schema findings; save/load, owner death, transfer ordering and cleanup still require a complete proposed feature and test. See the [audited source manifest](../research/jesec/feature-audit.json) and [state handbook](../handbook/state-and-values.md).

For a cross-generation workflow, define an explicit owner, replacement-owner condition, state initialization, pending action marker, reward guard and termination cleanup. Do not promote the existing delayed-event fixture into a proven cross-generation template merely because stories exist. Its [runtime blocker](../examples/test-runs.md) remains.

## Councils, governments, holdings and resource values

The archived `Council_modding` page distinguishes `common/council_positions` from `common/council_tasks`, and warns about positions without tasks and new-game initialization. Treat the crash warning as historical guidance to test, not as a confirmed Crozier failure for every configuration. Current native council references and position/task consumers must establish the exact task's scopes, liege/councillor/target bindings, progress and result callbacks. Do not confuse a council position with a court physician court position. Use the [subsystem guide](../systems/subsystem-guide.md) and current [developer-reference index](native-info-index.md).

The archived government page is only a pointer to `common/governments` and `_governments.info`; it supplies no complete modern administrative/nomadic/theocratic contract. The [Crozier migration](../systems/crozier-migration.md) and [religion/rites](../systems/religion-rites.md) already describe the important current changes. The legacy audit adds a concrete distinction between government identity, flags and `government_has_mechanic`. Shared identity does not imply shared influence, merit, herd or religious permissions.

`Holdings_modding` (labelled 1.3) distinguishes holding definitions, buildings, localization and generated build-cost/build-speed modifiers. Its repeated `game/game` paths are not reliable literal installation paths, and its statement about putting a DDS in a game-concept directory needs an actual asset consumer before adoption. The [legacy source map](../research/jesec/more-legacies-map.md) provides observed church-holding generated modifier uses; modifier formats/current holding definitions remain the authority. No custom holding or extra building slot was tested.

`Resources_modding` (labelled 1.2) points to common basic values for cost tiers and piety gains/losses. Numeric values, gain helpers and cost fields are different layers. For a new payment, use one audited value for preview and debit, read current helpers and DLC/game rules, then test exact before/after balances. The existing [payment contracts](../workspace/function-contracts.md) and fixture tests are more precise than the old small resource page.

## History, dynasties and display titles

`History_modding` (1.1), `Characters_modding`, `Dynasties_modding`, `Title_modding` and `Bookmarks_modding` explain connected identities: object definition, historical holder/liege, character dates, dynasty/house IDs, names, motto, coat of arms and bookmark presentation. A history entry is not a definition of a new landed title, and changing a historical liege is not automatically changing de jure organization. Test each intended bookmark in a **new game**; history date blocks are initialization data, not scheduled future gameplay events. Existing handbook/subsystem discussions cover this separation; exact load/merge behavior remains feature-specific.

The archive's dynasty page covers base dynasties/houses, not the legacy/perk purchase system. These are now explicitly separated by the new [Dynasty legacy reference](../systems/dynasty-legacies.md). Preserve unique IDs and localization prefix whitespace. Do not reuse the article's example numeric character/dynasty IDs as a new mod's collision-free namespace.

`Flavorization` explains eligibility/priority for displayed ruler/title names and suggests customizable localization for additional conditions. This expands the research map beyond simple literal names. A displayed title is not the landed-title ID or government identity. A very high historical example priority is a demonstration, not a compatibility-safe rule. Audit current flavorization `.info`, matching entries, localization scope and competing candidates before choosing priority. No new flavorization implementation was certified.

## GUI, graphical assets, fonts and export pipelines

`Graphical_assets` discusses portrait palette size, channel format and mipmaps. These are **portrait palette** recommendations, not interchangeable recipes for dynasty icons, framed GUI textures, terrain textures or 3D model materials. Keep the actual consumer and encoding/frame/container contract together. Existing [GUI/tools](../systems/crozier-gui-tools.md) and [graphics fixture tests](../examples/test-runs.md) retain their open frame/render issues. More Legacies supplies ID-matched icon and illustration filenames; no artwork was copied or rendered by this supplement.

`Exporters` and `3D_models` document a historical Clausewitz Maya/Photoshop pipeline, deployment settings, material/channel packing, meshes and animations. Vendor plugin paths, supported Maya versions, download availability and Blender alternatives must be verified for the chosen pipeline. No exporter was installed or invoked. Prefer the current relevant native `.info` and a test asset before a publication-quality content export; do not execute deployment instructions from the archive automatically.

`Fonts` discusses asset replacement and licenses. The suggestion to rename TTF to OTF is **not an accepted conversion procedure** here; neither that shortcut nor current engine compatibility was established. Select a correctly licensed font, verify its actual format and required glyphs, inspect the current font consumer/path, then test multilingual text, scaling and capitalization. A “free font” label does not settle redistribution terms. No font was changed.

## Terrain, struggles and reference catalogues

`Terrain_modding` expands orientation to terrain definitions, province terrain mapping, local terrain-generated modifiers, battle effects, travel/provision/fertility and associated assets/localization. Its own discussion of generated-modifier loading restrictions is a warning to check database initialization, not a universal allowance for generated fields in every file. Terrain/province/color/topology/pathfinding dependencies require an actual map-feature audit; no independent map functionality is introduced here.

`Struggle_modding` describes regions, cultures/faiths, involved/interloper eligibility, phases, transitions, catalysts, ending decisions and parameters with separate modifier groups. A parameter name displayed in a tooltip need not itself execute the promised action; trace the consumer. Its “three categories” sentence enumerates four groups, an internal inconsistency. Do not copy its large placeholder-containing example as a complete working definition. The legacy audit gives a focused current example: Crozier FP2 tracks add the viewer's Iberian involvement alongside dynast-based conditions. A new struggle remains a separate full audit/test task.

`List_of_baronies` is a historical ID catalogue. Use current installed landed-title/history/province mapping rather than assuming listed IDs or ownership still match the chosen bookmark. Artifact, culture, religion, regiments, lifestyle, title, trait, map, coat-of-arms and audio pages otherwise map to existing chapters in the ledger. Historical nested faith examples are superseded by current [separate faith/rite databases](../systems/religion-rites.md). Numeric trait indexing explicitly marked obsolete in the archive is not a new allocation scheme.
